# ADR-0010：榜单只发布 T0 / T1（取代 ADR-0002 的展示预算）

- 状态：已接受
- 日期：2026-11-05
- 决策人：YH
- 影响面：`src/engine/tierlist_export.py`、`src/renderers/ttk_report.py`、README、24 份距离榜文档、`data/榜单/*.json`、`tests/test_renderers.py`、`tests/test_tiering.py`、`tests/test_board_publication.py`

## 背景

ADR-0002 的规则是「T0 全列 + T1 列前 100 行」，T2/T3 仅存 JSON。运行一段时间后
暴露出两个问题：

1. **T1 被截断**：修脚情景每个距离带 T1 有 400+ 行，只列前 100 行，剩下的 T1
   既不在文档里、也不在读者预期里（页头虽写明，实际没人会去翻 JSON）。
2. **T2/T3 仍在发布物里**：JSON 携带全部 T2/T3 行，文件 10–12 MB，榜单的「信号
   密度」被稀释；对外消费方拿到的仍是全量分布，与「这是强度榜」的定位不符。

YH 2026-11-05 明确口径：**榜单只列 T0–T1 的枪**。

## 决策

1. **对外发布层级 = T0 / T1**（`PUBLISHED_TIERS`），判定按「任一带」：
   一把枪只要在某个距离带进入 T0/T1，就进该带的榜单；跨带 T2/T3 不额外删行。
2. **序列化层过滤**：`tierlist_export.to_export()` 只落盘 T0/T1 条目，
   且每条目的 `bands` 只保留 T0/T1 的带（跨带的 T2/T3 记录同样不发布）。
   T2/T3 仍参与 `assign_tiers` 的分位阈值计算（阈值本身依赖全量分布，不能砍），
   只是不写进 `data/榜单/*.json`。payload 保留 `ranked_entry_count`（全量）
   与 `published_entry_count`（发布），两者差额即未发布的 T2/T3 行数。
3. **文档全列 T0/T1**：取消 `T1_DISPLAY_LIMIT`，页头改为
   「只发布 T0 / T1 —— T0 共 X 行、T1 共 Y 行，均全列；T2 / T3 仅参与层级阈值计算，不发布」。
4. **README 分层行**同步改为「只发布 T0 / T1（全列），T2/T3 仅参与阈值计算」。

## 后果

- 主榜（5-5）每带：T0 90 + T1 150 = 240 行全列（此前 190 行，T1 尾部 50 行不可见）。
- 修脚每带：T0 282 + T1 468 = 750 行全列；文档体积约翻倍（~200 KB/份），
  换来「文档即完整 T0/T1」，不再有「见 JSON」的暗门。
- `data/榜单/*.json` 体积下降约 60%（只留 T0/T1）。
- 排名 `#` 仍是全量名次（T1 末行之后才轮到未发布的 T2/T3），
  页头「未列出的行排名均在本表末行之后」继续成立。
- 只影响发布层，TTK / 分层阈值逐位不变；`--price-only` 无需感知。

## 否决的方案

| 方案 | 否决理由 |
| :-- | :-- |
| 保留 T1 前 100 行截断 | 与「只列 T0–T1」直接冲突：同属 T1，一半发布一半不发布，规则不自洽 |
| JSON 保留 T2/T3、仅文档截断 | 对外数据仍混入 T2/T3，消费方无法区分「榜单」与「全量枚举」 |
| 只发布 T0 | 丢失 T1 这一档，榜单区分度不足；YH 口径明确含 T1 |
